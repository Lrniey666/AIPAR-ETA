# LLM 閘道

最後更新：2026-09-18（台北時間）

設計依據是 `AIPAR-ordering-system-sesearch/free-llm-api-test` 的實測結論：
全部走 OpenAI 相容 wire format，換一家只換 `base_url` / `api_key` / `model` 三個字串，
所以整個專案不依賴任何 LLM SDK，只用 Node 內建 `fetch`。

## 供應商

`src/llm/providers.ts` 每次呼叫都重讀環境變數，改 `.env` 重啟容器即生效。

| key | 預設 base_url | 視覺 | 備註 |
| --- | --- | --- | --- |
| `groq` | `https://api.groq.com/openai/v1` | 視模型而定 | 延遲最低，排文字第一棒。預設帶 `reasoning_effort=low`，避免思考吃光 `max_tokens`。 |
| `gemini` | `https://generativelanguage.googleapis.com/v1beta/openai` | ✓ | 免費層裡中文菜單辨識最穩，排視覺第一棒。 |
| `mistral` | `https://api.mistral.ai/v1` | ✓ | 月額度大但約 1 req/s，適合批次不適合高併發。 |
| `iai` | `https://www.iai.nkust.edu.tw/aihub/v1` | ✓ | **按 token 計費，不是免費層**，預設關閉。 |
| `local` | 由 `LOCAL_LLM_BASE_URL` 指定 | ✓ | 本機 Ollama 之類的保底，排最後。 |

### 三條略過規則

1. **沒填金鑰＝略過**，不是錯誤。0 家、1 家、N 家都要能正常啟動。
2. **有金鑰但沒填模型 ID＝略過並記原因**，不拿猜的 ID 去打 404。免費層模型會下架改名，
   `.env.example` 因此刻意不給「保證可用」的預設值。
3. **計費服務預設關閉**。PLAN 要求只用免費 API，`iai` 要 `LLM_ALLOW_METERED=true` 才會被納入。

被略過的供應商與原因會出現在啟動日誌與 `GET /health`。

## 換手策略

`src/llm/gateway.ts`。順序是 `provider1/key1 → provider1/key2 → provider2/key1 → …`

| 狀況 | 動作 |
| --- | --- |
| 429 / 5xx / 連線錯誤 | 同一把重試一次（聽 `Retry-After`，上限 4 秒），再不行換下一把 |
| 401 / 403 | 這把金鑰無效，立刻換下一把 |
| 400 | 請求本身有問題，跳過這家剩下的金鑰，直接換下一家 |
| **回覆為空** | 當成這家失敗，換下一家 |
| **要 JSON 卻挖不出來** | 當成這家失敗，換下一家。`menu-vision`／`menu-text` 會開 `require_json` |

最後兩條是實測踩到的：Gemini 免費層常把 `max_tokens` 花在思考上、正文留空；
直書密排菜單則會回一長段無法 `JSON.parse` 的字。以前閘道當成成功，上層只會丟
「模型沒有回傳可解析的 JSON」、Mistral 根本沒上場。

等待上限刻意壓在 4 秒內——Discord 互動不能讓使用者等一分鐘。

每一次呼叫（成功或失敗）都會寫進 `llm_calls`，寫入失敗不影響主流程。

## 任務

| 模組 | 任務名稱 | 用途 |
| --- | --- | --- |
| `tasks/menu_extract.ts` | `menu-vision` / `menu-text` | 菜單圖片或雜亂文字 → 結構化草稿 |
| `tasks/order_parse.ts` | `order-parse` | 自然語言 → 菜單品項 × 數量 |
| `tasks/order_cancel.ts` | —（純規則） | 自然語言取消：全部、指名品項、或請使用者講清楚 |
| `tasks/intent.ts` | `intent` | 查菜單、開團、點餐、取消、查帳、求助還是閒聊 |
| `tasks/reply.ts` | `reply` | 一般問答，支援串流；帶事實區塊與最近對話，回完還要過一次守門 |
| `domain/dish_query.ts` | —（純規則） | 「有沒有豆腐鍋可以吃」抽出菜名，改查 `menu_items` |
| `domain/recommend.ts` | —（純函式） | 「推薦吃什麼」從 `menu_items` 抽幾樣；加購項目不列入 |
| `domain/memory_capture.ts` | —（純規則） | 從一句話抓出要長期記住的事 |

### 兩條紅線

**一、價格永遠來自資料庫。** LLM 只負責「指到哪一項、要幾份」，
`unit_price_cents` 一律從 `menu_items` 取。模型會編價格，資料庫不會。

**二、規則優先、模型墊底。** 點餐、意圖判讀、菜單文字解析都先跑規則；
規則對得到就不打 LLM。免費層配額有限，而且規則比模型穩定可預測。

菜單擷取的正規化（`domain/menu_draft.ts`）刻意嚴格：**價格不是數字就整筆丟掉**，
寧可少一筆，也不要把幻覺價格寫進資料庫。

### 點餐數量：品名裡的數字不是份數

`order_parse.ts` 先比對品名，再從「品名沒吃掉的殘字」讀份數。
舊版反過來——先在整句抓數字當份數、再把數字連同量詞刪掉——於是
「三杯雞飯」變成三份「雞飯」，「牛三寶麵」「四季豆」「雙拼」也一起遭殃。
提示詞也補了同一條規則，模型走同一套判準。

只認三種份數寫法：數字接量詞（`3份`）、`x`／`×` 接數字（`x2`）、句首單獨的數字或中文數字。
讀不到就是 1——沒講就是一份，比猜一個數字安全。上限 20 份。

## 接地與防幻覺

`src/domain/grounding.ts` ＋ `src/bot/chat_context.ts` ＋ `src/bot/handlers/message_chat.ts`。

**要解的問題**（實際發生過）：使用者問「四海豆漿大王有甚麼好吃的」，那間店在資料庫裡，
但**還沒建菜單**，bot 卻列出四道不存在的菜。追下去有三個破口：

| 破口 | 修法 |
| --- | --- |
| `search_restaurants()` 拿**整句**去比店名，方向反了，所以查無餐廳 | `find_mentioned_restaurants()` 改成拿店名比句子 |
| 「有甚麼」沒被正規化成「有什麼」，意圖判成閒聊 | `fold_variants()` 折異體字，`normalise_key()` 也吃得到 |
| 查不到就掉進模型，而模型只拿到一張店名清單 | 事實區塊一律標注菜單狀態；路由先擋 |

### 四道防線（順序不能換）

```
1. 路由        完整講出店名        → 菜單 Embed 或「還沒建菜單」，不進模型
               問某道菜在哪家有    → 查 menu_items，不進模型
               只對到部分店名      → 先問「你是說 X 嗎」再附菜單
               要推薦／幫忙挑      → 從 menu_items 抽真實品項，不進模型
               問帳／問記憶／求助  → 查資料庫，不進模型
2. 事實區塊    build_facts_block()：餐廳一律標「菜單 v1．12 項」或「**尚無菜單**」
3. 系統提示    文字回覆**不得**出現菜名或價格；標「尚無菜單」的店要照實說不知道
4. 輸出守門    looks_like_invented_menu(text, known_names)：
               出現金額 → 擋；兩行以上條列「不認得的東西」→ 擋
```

第四道是因為免費層的小模型即使提示詞寫得很清楚，仍然會照著店名編。

**守門要抓得準，不能抓得寬。** 第一版把所有兩行以上的條列都當成編造，
結果連「要不要看看這兩家」都被換成罐頭句，反而更難溝通。
現在：金額一律擋（事實區塊裡從來沒有價格，講得出來就是編的）；
條列則只擋「不認得的東西」——帶 `/` 的行（指令）與**列出已知店名**的行都放行。
攔下來時會寫進日誌。

### 路由不能太貪心

防幻覺做過頭的樣子長這樣：使用者連問「推薦吃甚麼」「幫我挑」「給我麵店」，
三次都收到一模一樣的餐廳清單 Embed。沒有一句是假的，但也沒有一句是在回答他。

所以路由的判準不是「跟吃有關就攔下來」，而是**「資料庫回答得了這個問題嗎」**：

| 問句 | 資料庫答得了嗎 | 走哪 |
| --- | --- | --- |
| 「老余麵店有什麼」 | 答得了（有菜單） | 菜單 Embed |
| 「四海有什麼」 | 答得了（沒菜單＝不知道） | 照實說還沒建 |
| 「有沒有豆腐鍋」 | 答得了（查品項） | 品項 Embed |
| 「推薦吃甚麼」 | 答得了（抽真實品項） | 推薦 Embed |
| 「你喜歡賽馬娘嗎」 | 答不了 | 交給模型 |
| 「今天天氣真好」 | 答不了 | 交給模型 |

答不了的就該讓模型去接話——它手上有事實區塊，講得出店名但講不出不存在的菜。

### 記憶

| 種類 | 存在哪 | 誰決定要記 |
| --- | --- | --- |
| 短期 | `conversation_turns`，依頻道留最近 40 筆 | 自動，每一輪都記 |
| 長期 | `memory_facts`，依 user／channel／guild | **只記使用者明講的**（`domain/memory_capture.ts` 的規則） |

模型拿得到短期對話（當成真的 chat messages）與長期事實（放在事實區塊裡），
但**不能寫入任何一邊**——讓模型決定要記什麼，等於讓它把推測變成日後的事實。

「你有記憶功能嗎」這類問題由程式回答（`is_memory_question()`），
不讓模型自己說——它會答「我沒有記憶功能」，而那是錯的。

### 身分

每次回答都會帶上伺服器名稱、頻道名稱與發問者顯示名稱，
短期對話裡的使用者發言也前綴發話者，多人頻道裡模型才分得出「我」是誰。
發問者的顯示名稱同時寫進 `app_users`，網站與帳務才顯示得出人名而不是一串 id。

## 菜單 OCR 對帳

`src/llm/ocr.ts` ＋ `src/domain/ocr_layout.ts` ＋ `src/domain/menu_reconcile.ts`。

**要解的問題**：直書菜單（由上而下、由右至左）與躺著拍的照片，視覺模型會把同一欄的字拆散，
或把相鄰兩欄的品名與價格配錯對。`PLAN/example/menu_example/` 裡兩種都有。

**作法**（Compose 預設啟用：bot 打同網路的 `ocr` 服務。本機不走 compose 且沒設 `OCR_BASE_URL` 才整段略過）：

```
圖片 ──► OCR（PP-OCRv6 small）──► 文字框＋座標
                                    │
                    ┌───────────────┴───────────────┐
                    ▼                               ▼
          版面判定＋閱讀順序                   對帳：草稿 vs OCR
          （直書右→左、橫排上→下）          品名找不到＝❓
                    │                        價格找不到＝⚠️
                    ▼                        OCR 有、草稿沒有＝提示
          附進視覺模型的提示詞當對照
```

| 判定 | 依據 |
| --- | --- |
| 直書 / 橫排 | 多字文字框的長寬比投票（高 > 寬 × 1.6 算一票直書） |
| 閱讀順序 | 直書右→左、欄內上→下；橫排上→下、列內左→右。同列／同欄容差＝字框短邊的一半 |
| 對帳 | 品名在 OCR 全文裡找得到、價格數字也出現過 → `verified`；否則標記 |

**對帳只標記，不自動改資料。** OCR 會讀錯，模型會編造，兩者留下的痕跡不同：
編出來的價格在圖上根本不存在，讀錯的價格會在附近出現。標出來讓按下「確認寫入」的人
知道該盯哪幾行，比自動二選一可靠。人工關卡仍然不能省。

線上格式吃兩種（`.env.example` 有完整範例）：本專案約定的 `{"lines":[…]}`，
以及 PaddleOCR hubserving 的 `{"results":[[…]]}`。認不得的形狀回空陣列，
安靜退回純視覺流程，不讓整支 `/菜單 上傳` 失敗。

本倉的 OCR 服務在 `ocr/`：PP-OCRv6 small 的 ONNX 權重放 `ocr/models/`，
HTTP 入口是 `POST /ocr`，Compose 服務名 `ocr`（映像 `aipar-eta:ocr`）。
**不要跑在 bot 容器裡**，也不要在執行期去讀研究倉路徑。
權重遺失時在 `ocr/` 跑 `node scripts/fetch-models.ts`。

## 驗證

```bash
npm run llm:check
```

每家送一次極短請求（文字一次、視覺一次），印出延遲與錯誤原因。
「`.env` 填了」不等於「打得到」，上線前與部署後都該跑一次。
計費供應商預設被擋掉，這支不會誤打。

OCR 的狀態（有沒有啟用、指到哪個服務）印在 bot 啟動日誌，也在 `GET /health` 的 `ocr` 欄位。
