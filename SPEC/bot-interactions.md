# Discord 互動設計

最後更新：2026-09-18（台北時間）

## 原則

取自 PLAN §Discord bot互動設計，這幾條是驗收會看的：

1. **Embed ＋ 按鈕／下拉為主，不用 Modal。** 需要多行輸入的場合（貼菜單）改成「請貼一則訊息」，
   由 `PendingStore` 記住誰在等著貼，10 分鐘內有效。
2. **自然語言也能操作**，但碰到點餐與帳務一定用 Embed 回覆，不用純文字。
3. **等待時要有回饋**：訊息類互動先加 Ack Reaction（👀），需要等 LLM 生成的再加 Streaming Preview
   （先回一則訊息，每 1.2 秒把已生成內容編輯進去）。斜線指令則用 `deferReply()`。
4. **指令名稱**中文不超過 6 字、英文不超過 10 字母。
5. **在地化**：預設名稱與說明為英文（英式拼法），`zh-TW` 與 `zh-CN` 都對應到同一份繁體中文。
6. **視覺識別**：Embed 一律用 `src/bot/branding.ts` 的配色與標誌。標誌取自網站的 `/assets/`，
   沒設定 `PUBLIC_BASE_URL` 就不放圖——少一張圖仍然完整可讀，破圖不行。

| `/menu` | `/菜單` | `show`／`查看`、`upload`／`上傳`、`input`／`輸入`、`version`／`版本` | 菜單查詢與維護 |
| `/groupbuy` | `/揪團` | — | 在論壇開一場揪團 |
| `/settle` | `/結算` | — | 結算並寫入帳本 |
| `/ledger` | `/帳務` | `mine`／`我的`、`all`／`總覽`、`who`／`誰欠誰`、`pay`／`付款` | 帳務查詢與記錄付款 |
| `/memory` | `/記憶` | `mine`／`我的`、`save`／`記住`、`forget`／`忘記` | 看／改 bot 記得你的哪些事 |
| `/help` | `/說明` | — | 使用說明（五個編號欄位＋網站連結按鈕） |
| `/website` | `/網站` | — | 給出網站連結按鈕 |

`restaurant` 選項一律開自動完成，回傳值是資料庫 id，處理器不用再猜使用者指的是哪一間。

`/揪團` 的選項：

| 選項 | 型別 | 說明 |
| --- | --- | --- |
| `restaurant`／`餐廳` | 字串（自動完成，必填） | 餐廳 id |
| `minutes`／`截止分鐘` | 整數 1–10080 | 距現在幾分鐘截止。**只收數字**，不再接受 `1h30m` 這種寫法 |
| `payer`／`收款人` | 使用者 | 先墊錢的人，預設是開團者；結算時的債務對象 |
| `title`／`標題` | 字串 | 貼文標題 |

`/帳務 付款` 的 `to`／`付給` 指定收款對象。有指定才會抵銷債務關係，沒指定只動個人結餘。

### 移除的指令

`/order`（`/點餐`）在 0.3.0 移除。貼文裡已經有「點餐」按鈕與自然語言兩條路，
再留一支只能在貼文裡用的斜線指令只是多一個要解釋的入口。

## 元件 custom id

格式 `scope:action:參數…`（Discord 上限 100 字元），編解碼在 `src/bot/components.ts`，
揪團的元件建構子在 `src/bot/components_order.ts`。

| scope | action | 參數 | 說明 |
| --- | --- | --- | --- |
| `session` | `pick` | session | 開點餐面板 |
| `session` | `qty` | session, page | 改每項數量，整個面板重畫 |
| `session` | `add` | session, page, qty | 送出選好的品項 |
| `session` | `page` | session, page, qty | 品項翻頁 |
| `session` | `mine` | session | 看自己點了什麼 |
| `session` | `clear` | session | 開清除面板 |
| `session` | `remove` | session | 清掉選中的幾筆 |
| `session` | `clearall` | session | 清掉自己全部 |
| `session` | `refresh` / `lock` / `settle` | session | 重整、封單、結算 |
| `draft` | `confirm` / `cancel` | menu | 菜單草稿寫入或丟棄 |
| `menu` | `page` / `activate` | menu | 菜單翻頁、切換版本 |
| `restaurant` | `show` | — | 沒指定餐廳時的下拉選擇 |

`lock` 與 `settle` 只有開團者或具「管理伺服器」權限的人能按。

**數量為什麼編在 custom id 裡**：Discord 的多個下拉彼此不共享狀態，
選了數量再選品項時，第二個互動拿不到第一個的值。把數量寫進品項下拉的 id，
改數量就重畫面板，是唯一不必另建暫存的作法。

## 三條主要流程

### 功能一：菜單建檔與查詢

```
/菜單 上傳 ──► 下載圖片 → OCR 版面分析（選用）→ 視覺模型 → 草稿（status=draft）
                              │                        │
                              │  直書／橫排判定、閱讀順序 │
                              └──► 對帳：草稿 vs OCR ────┤
                                                        ▼
/菜單 輸入 ──► 規則解析；解析不出來才交給 LLM ──► Embed 預覽 ＋［確認寫入］［取消］
                                                        │ 確認
                                                        ▼
                                          activate_menu()：新版上線、舊版封存
```

沒有人按下「確認寫入」就不會有 `active` 菜單——辨識實驗的結論是自動化天花板不高，人工關卡不能省。
對帳沒核對上的品項在預覽裡標記：`⚠️`＝品名對得上但圖上找不到這個價格，`❓`＝連品名都對不上。
細節見 `llm-gateway.md` §菜單 OCR 對帳。

### 功能二：揪團點餐

```
/揪團 ──► 讀 guild_settings.forum_channel_id 與 notify_role_id
       ──► 論壇建立貼文，第一則訊息 ping 身分組＋菜單 Embed
       ──► 送出彙總訊息（Embed ＋ 按鈕），記下 summary_msg_id
            │
            ├─ 按［點餐］→ 選數量（1–10）→ 下拉複選品項（每頁 25 項）
            ├─ 按［清除我的］→ 逐項選要清掉哪幾筆，或［全部清除］
            ├─ 直接打字 →「我要兩個雞腿飯跟一杯紅茶」
            └─ 直接打字 →「取消紅茶」「全部取消」
            │
            ▼
       每次加點或取消都重畫彙總訊息（全體清單 ＋ 每人應付）
```

貼文裡對不到菜單的閒聊**不會**被當成點餐；有 @ 到 bot 時才轉去自然語言問答。

**彙總訊息的截止時間**：只有還開著、而且時間還沒到，才顯示會自己倒數的相對時間戳記；
已封單或時間已過就寫死「截止」＋實際時刻。倒數字樣會讓人以為還能點，
而且每個用戶端都還在幫一個早就結束的時間算差值。

**封單只有一條路**：`session_flow.lock_session()`。手動按鈕與排程自動封單都走它，
改狀態、貼文標題加 🔒、貼通知、重畫彙總，四件事一次做完。

### 功能三：記帳

```
/結算 或［結算］──► settle_session()：每人小計寫成 ledger charge（同場同人只寫一次），
                     charge 記下對象＝這場的收款人（payer_user_id）
                 ──► 貼文狀態改 settled，並告訴大家把錢拿給誰、共多少
/帳務 付款 ──────► 寫一筆 payment；指定「付給」才抵銷債務關係
/帳務 我的 ──────► 個人結餘 ＋「你要拿 X 給某某」「某某要還你 Y」
/帳務 誰欠誰 ────► 全體債務（互抵後）＋ 最少轉帳建議
/帳務 總覽 ──────► 每個人的結餘
```

**結餘與債務是兩件事**，Embed 也分開呈現：

- 結餘＝這個人吃了多少、付了多少（`ledger_entries` 的加總）
- 債務＝這個人該把錢拿給誰（有 `counterparty_user_id` 的那些紀錄，收斂邏輯在 `domain/debts.ts`）

只有結餘的時候，使用者知道自己欠 250 卻不知道要給誰——這是 0.3.0 補的。

## 自然語言

規則優先、模型墊底（`SPEC/llm-gateway.md` 的第二條紅線）。
**能用資料庫確定回答的，就絕對不要交給模型**——這不只是省配額，是防幻覺的第一道防線。

被 @ 到時的判斷順序（`src/bot/handlers/message_chat.ts`）：

| 順序 | 條件 | 處理方式 |
| --- | --- | --- |
| 1 | 問到記憶（「你有記憶功能嗎」） | 程式回答記得多少，不讓模型自己說 |
| 2 | 明講要記住的事 | 寫進 `memory_facts` 並確認 |
| 3 | **完整**講出已建檔的店名 | 有菜單 → 菜單 Embed；**沒菜單 → 照實說還沒建**。不進模型 |
| 4 | 問某道菜在哪家有 | 查 `menu_items`，只答資料庫裡真的有的。不進模型 |
| 5 | 只對到店名的**一部分** | 先問「你是說 X 嗎？」再附上菜單，不要裝作聽懂了 |
| 6 | `recommend`（推薦、幫我挑） | 從 `menu_items` 抽幾樣真的存在的。不進模型 |
| 7 | `help` | `/說明` 的 Embed |
| 8 | `ledger-query` | 帳務 Embed（含債務） |
| 9 | `menu-query`（明著要看清單）且沒指到店 | 餐廳清單，每一間都標菜單狀態 |
| 10 | 其他 | 才交給模型，帶事實區塊與最近對話，回完再過一次守門 |

**第 4 條要排在第 5 條之前**：「豆腐鍋」既是菜名、也是「雷荷豆腐鍋專賣店」的一段，
但問的人要的是「哪裡吃得到」，不是那家店的整份菜單。

**`recommend` 與 `menu-query` 是兩件事。** 第一版把兩者混在一起，
於是「推薦吃甚麼」「幫我挑」「給我麵店」通通回同一塊餐廳清單——
使用者問什麼都拿到同一個罐頭，反而比會編菜單更難溝通。
現在「要一個答案」走推薦（抽真實品項），「要一份清單」才給清單。

貼文裡的 `order` 與 `cancel-order` 另外處理（`message_order.ts`）：
價格取自 `menu_items`，取消規則對不到就問清楚，不讓模型猜要刪什麼。

金額、品項、誰欠誰一律取自資料庫再交給 Embed，不讓模型轉述數字。
完整的四道防線見 `SPEC/llm-gateway.md` §接地與防幻覺。

## 記憶與身分

| 種類 | 範圍 | 保留 | 誰決定要記 |
| --- | --- | --- | --- |
| 短期 | 頻道 | 最近 40 筆 | 自動 |
| 長期 | 使用者／頻道／伺服器 | 直到被忘記 | **只記使用者明講的** |

每次回答都認得出伺服器、頻道與發問者；發問者的顯示名稱同時寫進 `app_users`。
使用者用 `/記憶 我的` 看得到全部，`/記憶 忘記` 刪得掉（留空＝連短期對話一起清）。

## 語言判定

| 來源 | 判定方式 |
| --- | --- |
| 斜線指令／元件 | `interaction.locale`，`zh*` → 繁體中文，其餘 → 英文 |
| 一般訊息 | Discord 不給使用者語言，改看伺服器 `preferredLocale`，再退回「內容有沒有中文」 |

## 背景排程

`src/bot/scheduler.ts` 每 60 秒掃一次 `deadline_at` 已過但仍 `open` 的揪團，
呼叫 `lock_session()` 自動封單並在貼文裡通知。
單次掃描失敗只記錄、不讓計時器停掉（驗收要求連跑一週）。

## Intents

`Guilds`、`GuildMessages`、`MessageContent`、`GuildMessageReactions`。

**`MessageContent` 是特權 Intent**，必須先到 Discord 開發者後台打開，否則 bot 收到的訊息內容會是空字串，
自然語言點餐與貼菜單都會失效。
